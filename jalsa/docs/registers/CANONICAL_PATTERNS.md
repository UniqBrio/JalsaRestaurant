# Canonical Patterns — Jalsa

> **One blessed idiom per concern.** Read the reference and mirror it. A second way of doing an
> already-solved thing is a defect, not a preference — it doubles the places a rule must be
> changed and guarantees one of them gets missed.
>
> Newest first. Append or supersede; never renumber, never delete.

| ID | Concern | The one way | Reference |
|---|---|---|---|
| JP-23 | A spec that asserts behaviour the code no longer has | The module's CONTRACT changed, or it did not. If it did not, the spec is right and the code is wrong — fix the code. If it did, rewrite only the assertions the contract invalidated, **in place**, and add a dated `SUPERSEDED` note at the top of the file naming what they used to assert and why that stopped being true. Never delete the record; never leave a green assertion about a rule that no longer exists. Registers are NOT covered by this — they stay append-only without exception, because a register entry is a fact about the past and cannot be invalidated by a contract. **Qualifying precedent (19-Sep-2026, Phase 1 printing):** `resolvePrinter` stopped reading `printer.online`. That is a contract change, not a bug fix — `online` is a snapshot of one second and `print_job.printer_id` became permanent, so routing on it would have assigned a momentarily-unplugged station's tickets to another machine forever, with no retry able to correct it. Four cases in `print-routing.unit.spec.ts` asserted the old fallback. Keeping them verbatim meant a red suite; deleting them meant losing the record. Eight lines were rewritten under this exception; five of those were forced by the contract itself. | `tests/unit/print-routing.unit.spec.ts` (the `SUPERSEDED ASSERTIONS` header) · `docs/modules/printing.md` · rung: `tests/unit/spec-supersession.unit.spec.ts` |
| JP-22 | A row of chips that is a NAVIGATION | `CHIP_NAV_WRAP` — `flex flex-wrap gap-2`. Every destination on the screen at every width; the row gets TALLER on a narrow phone and nothing is hidden to buy that. A FILTER strip is the other case and may scroll sideways (`ChipRow`, which carries the design set's right-edge fade so the cut is legible) — because every option there is the same kind of thing and the tail is a narrower view of a list still on screen. A destination nobody can see is a destination nobody can reach: `Printers & machines`, tenth of ten, sat in a `flex` row with no `flex-wrap` inside `overflow-x: auto` with the scrollbar hidden on both engines. Never buy the fit with smaller text, `shrink`, ellipsis or `overflow: hidden`. | `src/lib/chip-nav.ts` · `src/features/owner/sections/SettingsSection.tsx` · rung: `tests/render/settings-submenu.render.spec.ts` (ten chips measured at eight widths) |
| JP-21 | Narrowing a table | A filter control in the COLUMN HEADER it acts on, never a filter bar above the table: a strip of screen paid for whether or not anyone is filtering, and a second place to look. Three kinds only — `text` (contains), `options` (a closed list, built from the rows on screen), `range` (two ends) — declared per column on `DataTable`, because one kind for every column offers a text box for a yes/no. Several values in ONE column are an OR; separate columns are an AND. Sorting stays on the header and is a different mechanism. | `src/lib/list-controls.ts` (`applyColumnFilters`) · `src/components/ui/column-filter.tsx` · `src/components/ui/data-table.tsx` · rung: `tests/unit/column-filters.unit.spec.ts` |
| JP-20 | A control the person expects to move NOW | The phone holds a DRAFT overlay and renders it over the server's answer; the write follows after a short collapse window, and the draft is dropped the moment the server replies — on failure too, so the row snaps back to the truth. Never `runBusy` on a per-row control: it disables every other row for the round trip and silently DROPS taps made during it. Anything that then reads the STORED state must await `flushCart()` first. | `src/lib/cart-draft.ts` · `src/features/guest/GuestApp.tsx` (`setCartQty`, `flushCart`) · rung: `tests/unit/cart-draft.unit.spec.ts` |
| JP-19 | Two boxes showing one number | Exactly ONE of them is the input — whichever the person typed in — and the other is a computed readout. Never two live inputs that are also cumulative: the moment both are filled the thing is applied twice. Only the typed one is sent, and the typed one is never rewritten under their fingers. | `src/lib/money.ts` (`mirrorDiscount`) · `src/features/owner/CloseBillSheet.tsx` · rung: `tests/unit/discount-mirror.unit.spec.ts` |
| JP-18 | Withdrawing a request the guest made | Return the row to the state before it, and KEEP the timestamp that records it happened. `open` plus a `payment_requested_at` is the paused state the phone reads; clearing it would erase the only evidence the request existed, and a request that vanished from a captain's screen without a trace gets blamed on the software. | `src/lib/db/mutations.ts` (`withdrawPaymentRequest`) · rung: `tests/functional/closure-upsell-tip.functional.spec.ts` |
| JP-17 | A write the screen must reflect | The write ANSWERS with the new state (`state` in the body) and the phone applies it. Never write-then-read: the server is next to the database and has just written it, while the phone's follow-up read is a round trip to another region — and can be two, because a read a person caused is never dropped (JP-13). No echo is still valid; the read is the fallback, not the plan. | `src/lib/db/guest-echo.ts` · `src/lib/write-echo.ts` · `src/hooks/useLiveData.ts` · rung: `tests/unit/write-echo.unit.spec.ts` |
| JP-16 | Clearing a fixed bottom bar | `ActionBar` measures ITSELF and renders an in-flow spacer of its own height. Never a constant clearance token used as the bar's height: the constant is only ever right for the bar it was measured against, and the next bar that grows a row hides the page's last element behind it — silently, on a phone, which is how the guest's order totals disappeared on 12-Sep-2026. The token survives only as the pre-measurement fallback. | `src/features/guest/GuestApp.tsx` (`ActionBar`) · rung: `tests/functional/guest-total-visibility.functional.spec.ts` ("nothing on the order screen sits underneath the bottom bar") |
| JP-15 | A default a person may override | The owner's setting seeds the guest's choice; the guest's control is always present and always wins for their own phone. The owner's switch is the DEFAULT, never a lock — `features.orderTotal` decides what the phone shows before anyone touches anything, and the tick box decides it after. | `src/lib/guest-features.ts` · `src/features/guest/GuestApp.tsx` (`TotalReveal`) · rung: `tests/unit/guest-features.unit.spec.ts` |
| JP-14 | A feature flag's default | ONE function, `resolveFeatures`, on both sides of the server boundary. The guest payload and the owner's Settings panel fill an unsaved key from the same table. Never a per-call-site guess such as "unsaved means on": it is right by luck until the first feature whose default is off, and then the switch and the phone disagree with nobody able to see it. | `src/lib/guest-features.ts` · `src/lib/db/guest-view.ts` · `src/features/owner/sections/SettingsSection.tsx` · rung: `tests/unit/guest-features.unit.spec.ts` |
| JP-13 | A read that proves a write | A refresh a PERSON caused is never dropped: if one is in flight it is remembered and re-run the moment that finishes. A refresh a TIMER caused is dropped freely. One boolean cannot serve both — dropping a tick costs nothing, dropping a confirmation costs a second round in the kitchen. The hook also compares the payload as text and skips `setState` when nothing changed, so an unchanged poll re-renders nothing. | `src/hooks/refresh-gate.ts` · `src/hooks/useLiveData.ts` · rung: `tests/unit/refresh-gate.unit.spec.ts` |
| JP-12 | A screen whose data did not load | Wrap the server-side read in `attempt()`. Three outcomes, always in this order: not configured → `NotConfiguredState`, unreachable → `UnreachableState`, loaded → the screen. Never a bare `await` in a server component: the throw becomes Next.js's error page, which tells a guest nothing and offers them nothing. | `src/lib/supabase/server.ts` (`attempt`) · all three of `src/app/{t/[table],staff,owner}/page.tsx` · rung: `tests/functional/degraded.functional.spec.ts` |
| JP-11 | A side effect after a state change | Compute the next value, call `setState` with it, then act on the value. **Never call a side effect inside a `setState` updater** — React 19 invokes updaters twice under StrictMode, so the effect happens twice and nothing on screen shows it. | `src/features/staff/PinSignIn.tsx` (`press`) · `src/features/staff/ChoosePin.tsx` · rung: `tests/functional/signin.functional.spec.ts` ("submits exactly once") |
| JP-10 | Reacting to props during render | Adjust state during render against a stored "last seen" value. No `useEffect` that calls `setState` — React 19's `react-hooks/set-state-in-effect` refuses it, and it renders twice for no reason. | `src/features/guest/GuestApp.tsx` · `src/features/owner/sections/LiveOrders.tsx` |
| JP-9 | Reading a value the browser owns | `useSyncExternalStore`, with an explicit in-memory fallback for the case where storage throws (private windows, blocked site data). | `src/theme/ThemeProvider.tsx` |
| JP-8 | Keeping a screen live | One idiom: `useLiveData` — 6s, stops when the tab is hidden, one request in flight, and **never blanks the screen on a failed poll**. No Realtime subscriptions: they would require a browser-reachable RLS policy, and the whole security posture rests on there being none. | `src/hooks/useLiveData.ts` |
| JP-7 | Anything a guest's phone asks for | An opaque token in a cookie, resolved server-side. The phone holds no bill id, no table id and no total — only a key. Closing the browser therefore loses nothing, and editing the cookie buys nothing. | `src/lib/sessions.ts` · `src/lib/db/guest.ts` |
| JP-6 | Anything a member of staff does | An HMAC-signed cookie naming them, checked against `Grants` on the server by `demand()`. The UI hides what it cannot honour; the server refuses it. Both read the same function. | `src/lib/sessions.ts` · `src/lib/db/mutations.ts` |
| JP-5 | Money | Integer rupees, everywhere. Percentage discount first, then flat, clamped to the subtotal. `payable` includes the tip; `restaurantIncome` excludes it. **There is deliberately no field called "total"** — the ambiguity is the bug. | `src/lib/money.ts` · rung: `tests/unit/money.unit.spec.ts` |
| JP-4 | Which table a bill is on | `bill_table` rows with `released_at`, never a `bill.table_id`. A bill belongs to one **or more** tables; an ordinary table is a group of one, so joining tables is not a special case. A partial unique index stops a second bill opening on an occupied table, and a trigger releases every table on closure. | `supabase/migrations/20260910070000_jalsa_core_schema.sql` |
| JP-3 | Closing a bill | Only a named member of staff, with a payment mode, recorded at a time — enforced by `bill_closure_is_attributed` in the database, not in application code. A guest can only ever *request* payment. | same migration · `src/lib/db/mutations.ts` (`requestPayment`, `closeBill`) |
| JP-2 | A number people read aloud | `next_number(restaurant, kind)` — `UPDATE … RETURNING` under a row lock. Bills, KOTs and table groups all use it. Never `max(n)+1`, which hands two captains the same KOT number on a busy night. | same migration |
| JP-1 | Colour | `design/tokens.json`, the only file in this repository containing one. Generated theme files are never hand-edited; application code references semantic tokens. | `design/tokens.json` · enforced by `npm run theme:check` and `audit:colors` |

## Two patterns this application deliberately does **not** have

**No GraphQL layer, and no second backend language.** The permission matrix has exactly one
enforcement point, in TypeScript, next to the code it guards. A resolver layer would be a second
place for "may this person see this bill?" to be answered, and the two would eventually disagree.

**No browser-side data client.** A guest's phone is an untrusted device sitting on a table in a
public room. If it could query PostgREST directly, "which bills may this phone see" would be a
question answered in SQL, separately from the same question answered in the UI.
