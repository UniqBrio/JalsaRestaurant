## A1 — WHAT ALREADY EXISTS (traced before any code, as the IMPLEMENTATION RULE required)

Four of the five states this request cares about are already built, and they are already distinct
from one another:

| State | Where it is handled today |
|---|---|
| Offline at the QR, service worker installed | `public/offline.html`, precached by `public/sw.js` and served for any navigation that cannot reach the server |
| Invalid / unknown QR | `UnknownTable` in `src/app/t/[table]/page.tsx` — a designed screen, never a 404, and **already distinct from offline** |
| Backend unreachable, customer online | `attempt('guest.page', …)` → `UnreachableState` |
| Connection lost mid-session | `OfflineBanner` — reads `navigator.onLine`, listens to BOTH window events, cleans up, and is non-blocking. Its copy already promises the session survives |
| Captain contact | the `callCaptain` guest feature, already wired to the existing request mechanism |

### The gap that is real, and app-owned

**`useLiveData` cannot tell a network failure from a server failure.**

```ts
const res = await fetch(url, { cache: 'no-store' });
if (!res.ok) throw new Error(`${url} ${res.status}`);   // HTTP 500 …
…
} catch (err) {                                          // … and a dead network land here together
```

A `TypeError: Failed to fetch` from a phone in a lift and an HTTP 500 from a broken query produce
the same message. The guest `send` path is the same: `throw new Error(parsed.message ?? 'That did
not go through.')`. So the request's central rule — *report connectivity failures as offline, and
do not label server errors as offline* — has nothing to act on. **That classifier is what this
change adds.**

### THE BLOCKER, STATED UP FRONT BECAUSE IT DECIDES WHAT CAN BE DELIVERED

**The screen a customer actually sees when they scan offline cannot be changed from this
application.** `public/offline.html` is GENERATED by `scripts/theme-build.mjs` — a file at the
**repository root**, which this request names read-only and forbids modifying. Its wording is
hardcoded in that generator, not driven by `design/tokens.json`, and hand-editing the generated
output is refused by the `theme-sync` audit and by the framework's rule that generated theme
files are never hand-edited.

It currently reads **"You are offline"** / *"This page could not be loaded because the device has
no connection."* with a **Try again** button — close to the requested wording in substance,
different in words. Changing it to the exact requested copy is a framework change, not a Jalsa
change, and is reported rather than smuggled in.

### A second limitation worth stating

On a customer's **first ever visit while offline** there is no service worker installed yet, so
the browser's own error page appears and no Jalsa screen can run at all. No web application can
avoid this.

### And an honesty point about "Call captain"

On a genuinely offline screen, a **Call captain button cannot work** — the existing mechanism
posts to the server. The request marks it optional. It is therefore NOT added as a button that
would fail silently; the offline copy points the customer at the person standing a few metres
away instead, which is what the shipped `/offline` route already does.
