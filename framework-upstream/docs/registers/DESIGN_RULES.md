# Design Rules

> Design lessons promoted into rules with IDs — so the third occurrence of a design mistake
> is prevented by process, not memory. Read at every design run
> ([docs/24 §1](../24-DESIGN-PLANNING.md), inspect-first step 1).
>
> **Append-only.** Newest first. Never renumber, never hard-delete; a superseded rule is
> struck through with a date and kept. IDs `DR-<n>`, never reused.
>
> **Every row names its enforcement rung as a path** — an executable check, or the checklist
> item that carries it — or declares itself prose-only, honestly.
> `scripts/audits/check-rule-coverage.mjs` parses this file and counts the answers; a new
> prose-only rule is a ratchet violation to take *knowingly*, not by accident.
>
> **How a row gets here:** a design correction the requester makes twice is a candidate
> (`workflows/promote.md` → `CANDIDATES.md`); promoted, it lands as a row via
> `/framework-update`. A one-off preference stays in that app's own rules — this register
> holds only lessons that generalise.

|---|---|---|---|
| DR-8 | **An arrangement is a function of the available space and what the content needs — never of a device name.** A multi-column form, a row of controls, a side-by-side pair: each is a decision that was correct at *some* width, and the question is what happens at the others. It must **change when the available width makes it materially less usable** — measured against control operability, label readability, room for helper and validation text to expand, touch operability, and whether the grouping still reads as a group. The permitted outcomes are all of: **keep the columns · stack · regroup selectively · make a control full-width**, and which one is right is decided by the content, not by a rule. **The threshold is the content's, not the device's.** `@media (max-width: 768px)` describes a screen; `minmax(<the practical minimum>, 1fr)` with `auto-fit` describes the requirement, and stays correct inside a narrow dialog on a wide monitor, in a split pane, and at a zoom level nobody tested — three cases no device breakpoint has ever caught. The practical minimum is **one declared number** (`design/tokens.json` → `layout.minFieldWidth`), for the same reason colour lives in one file: a threshold restated in the check that polices it drifts, and then passes because both sides moved. **What this rule does NOT restate:** that nothing scrolls sideways (DR-6's rung, already executed), and that a set of options too large to fit becomes a sheet (DR-6) — DR-6 is the narrow instance, this is the general case. **Not covered, declared:** whether a stacked order still *reads* as a group is design review; no scanner can judge it. | `rung: starter/tests/functional/responsive-fit.functional.spec.ts` — a width sweep from `layout.minSupportedWidth` to 1280 asserting no value-entry control falls under the declared floor (and, when the form is narrower than the floor, that one control takes essentially all of it), no label is clipped, and every button meets `layout.minTouchTarget`. Each assertion carries a companion "something was measured" check, so an empty selector cannot pass in silence. Implementation: `.form-grid` in `starter/src/components/components.css`. Helper/error-text expansion is **not** asserted — the reference form has none to measure — and is carried as review, honestly | Owner directive, 13-Sep-2026 |
| DR-7 | **On a multi-column data table, a filter belongs in the column it filters.** A small control in the header of each *filterable* column — not every column, and never one that merely repeats the sort. **Filtering and sorting stay separate affordances**: one arrow that both sorts and opens a filter menu means every attempt at one is a coin-flip risk of the other, and the user stops using both. The toolbar keeps only what crosses columns: the single search box and the date presets. **What this rule does NOT restate, because it is already built and already enforced** (`rung: starter/tests/unit/list-controls.unit.spec.ts`, `src/lib/list-controls.ts`): filters are independent and combinable — OR within a field, AND across fields — active ones are shown as `aria-pressed` chips that clear individually, **Clear all** is always visible once anything is active, and the count reads *matching / total* so a filtered table never reads as missing data. This row adds **placement only**, which is the one part none of that covers. **Why not a filter panel:** a panel or a growing toolbar pushes the data below the fold, so the user filters without being able to see the effect — and the effect is the entire reason they filtered. | Placement is **design review, declared** — no scanner can tell a header control from a toolbar one. The *behaviour* half is fully executed by CP-23's rung, unchanged by this rule. `COMPONENT_LIBRARY` carries the header control itself as a **GAP** | Owner directive, 12-Sep-2026 |
| DR-6 | **When a set of filters or categories does not fit comfortably on the screen, use a visible button that opens a compact sheet or grid. Avoid horizontal scrolling.** The button is *visible and labelled* — an icon alone is a guess, and the count belongs on it ("Categories · 12") so the user knows the size of the choice before opening anything. The sheet shows **every** option at once, in a grid, reachable with one thumb; choosing one **applies immediately and closes** — no Apply button, because a second tap to confirm a single choice is the interaction this rule exists to remove. What is currently chosen is visible on the button after it closes, or the user has to reopen the sheet to find out what they picked. **Why not a scrolling row:** the options past the right edge are not "harder to reach", they are never used, by anyone, ever — and that reads in the numbers as "nobody wants that filter" rather than "nobody could see it". It also fails silently: the row fits the designer's screen, so nothing looks wrong. Prioritise, in this order: **one-hand reach · fast discovery · fewest taps.** | `rung: starter/tests/functional/narrow-width.functional.spec.ts` — the mechanical half, executed at 360×640 on every run: the document may never be wider than its viewport, on the list, the empty state, an open dialog and an open dropdown. Screen checklist item 11 carries the same rule for a human reader. The *replacement* half — that what appears instead is a findable button opening a compact sheet — is **design review, declared**: no scanner can tell a good sheet from a bad one, and `COMPONENT_LIBRARY` carries the sheet itself as a **GAP** | Owner directive, 12-Sep-2026 |
| DR-5 | **Every dropdown is searchable, and every dropdown can grow.** On open it is **focused with the cursor already live**, so the next keystroke filters instead of being swallowed — and it **shows the existing options before a single keystroke**, because a box that starts empty asks the user to guess what is in it. Typing filters; no match offers **`+ Add "<what they typed>"`** inline, and the new option is **saved for future use**, not held for this one form — an option that disappears on reload teaches the user to distrust the control and to type the same thing again tomorrow. The added value goes through the same validation and lexicon check as any other stored term. The list, the search box, the highlighted match and the `+ Add` row all carry **declared contrast pairs in both themes** — a filtered list is where pale-on-pale text usually first appears, because the highlight colour is chosen for the light theme and never re-checked in the dark one. Applies to a native `select` too: if the set can exceed roughly seven options, or can grow, it is this control and not a `select`. | `CP-16` (focus and the live cursor, computable — already enforced) + screen checklist items 4 and 10 + `scripts/check-contrast.mjs` and gate **G2** for the contrast half. **AMENDED 12-Sep-2026 (v2.4.0) from "the search, + Add and persistence halves are a COMPONENT_LIBRARY GAP row, not code"** — they are now built: `rung: starter/tests/unit/select-options.unit.spec.ts` (15 cases: the duplicate that differs only by case or spacing, the empty query that must show everything, arrow bounds) + `starter/tests/functional/select.functional.spec.ts` (11 cases per project: the cursor live on open, the first keystroke filtering, `+ Add`, survival across a reload, Enter not submitting the form, Escape not closing the dialog, and the active row's computed contrast in BOTH themes). Implementation: `starter/src/components/SearchableSelect.tsx` + `starter/src/lib/select-options.ts`. The contrast case sits in the FUNCTIONAL tier deliberately — the gate does not run `test:render` (RC-016), so a rung placed there would be one nothing executes | Owner directive, 12-Sep-2026 |
| DR-4 | **A message to a user is written in the user's business language, and is as short as it can be while still saying what happens next.** Not "Validation failed on field `qty`" but "Enter how many". Not "Request completed successfully" but nothing at all — a silent success that simply shows the new state is shorter than any sentence about it. Three tests, all cheap: could the person who *asked* for this screen read it aloud to a customer · does every word appear in `PRODUCT_LEXICON.md` or in ordinary speech · does it say what to do next, or only what went wrong. **The technical half of this is already enforced** and is not restated here: the copy-gate reviewer blocks raw machine detail reaching a user — constraint names, error codes, `undefined`, stack traces — and `src/lib/errors.taxonomy.ts` classifies failures by *what the user must do about them*, never by where they came from. What this row adds is the positive obligation: brevity and business language, which no scanner can judge. **This set completes two rules that already exist and are NOT duplicated here** — an input is focused with the right keypad (screen checklist items 1 and 4, `CP-16`) and **Go/Enter submits and advances** (`CP-22`, asserted end to end against the DATA in `starter/tests/functional/keyboard.functional.spec.ts` — open, type, Enter, save). | Copy-gate review (`.claude/agents/copy-gate-reviewer.md`) + screen checklist item 19 + `docs/registers/PRODUCT_LEXICON.md`. **Prose-only for brevity and tone, knowingly**: a scanner cannot tell a terse label from a curt one, and a rule that fails on every short string would be switched off in a day | Owner directive, 12-Sep-2026 |
| DR-3 | **A tab must look like a control, and the selected one must be unmistakable.** Every tab carries a **visible border**, selected or not — a row of borderless labels does not read as a set of controls at all, and users find them by hovering, which does not exist on a phone. The selected tab differs in **three ways together — fill, border and weight** — because any one alone fails somebody: colour alone fails a colour-blind user, weight alone is invisible at a glance, a border alone disappears on a small screen. Where the selected state uses a background fill, that fill and its label must be a **declared contrast pair** (here `primarySurface` / `onPrimarySurface`), so a tinted tab never turns its own name into pale text on a pale wash. The styling hangs off `aria-selected`, so what is drawn and what is announced cannot disagree. | `rung: starter/tests/render/contrast.render.spec.ts` (computed contrast on the selected and unselected tab, both themes) + `starter/src/components/components.css` | Owner directive, 10-Sep-2026 |
| DR-2 | **A session ends when the user says so.** A signed-in session survives reload, navigation and backgrounding; it ends on explicit sign out, or on a security event the user is told about. This holds for JWT and username/password alike — a token that expires silently mid-task is indistinguishable, to the user, from the application losing their work. Sign out **confirms first** and sits under the overflow menu, isolated from daily actions. | Prose + the `COMPONENT_LIBRARY` Session rows; the confirm half is `starter/src/components/ConfirmDialog.tsx` | Owner directive, 06-Sep-2026 |
| DR-1 | **Sentence case for every visible string**, table cells included: capitalise the first letter and **leave the rest exactly as written** — lowercasing the tail turns "WhatsApp", "PDF" and every customer name into a typo. `rung: starter/tests/unit/text-format.unit.spec.ts` covers the utility; the rule over arbitrary strings is a **review** item on the copy pass — honest debt, because a scanner cannot tell a label from a code string. | `starter/src/lib/text-format.ts` + copy-gate review | Owner directive, 06-Sep-2026 |
