Design standard · version 1

Reusable Design Standards

Forty-four principles, generalised from the review notes on one real product so they apply to any application. Every one of them exists because a shipped screen was missing it and someone had to ask. Read the four questions on the last page before starting a build, and run the checklist before calling one finished.

How each entry is written. A one-line rule, why it earns its place, where it applies, and the component or interaction that implements it. Nothing here is specific to one product; anything that was has been left out.

SECTION ONE

Navigation and orientation

A user who cannot tell where they are, or cannot get somewhere without scrolling, is paying for your information architecture with their time.

1.1

Pinned primary navigation

The main section bar stays fixed while content scrolls beneath it.

Section switching is the most frequent action in a multi-section app. Making it cost a scroll-to-top taxes every move a user makes.

USE IN admin consoles, dashboards, settings areas, anything with more than three top-level sections
PATTERN Sticky header; horizontally scrollable when items overflow, with a right-edge fade so the cut is legible. Mark the active item by weight and an underline, never colour alone.
1.2

Sub-navigation gets the same treatment

Secondary tabs pin below the primary bar and stay visible while their panel scrolls.

Long settings and report areas are exactly where users hop between siblings most. Pinning the parent and not the child solves half the problem.

USE IN settings, reports, profile areas, anything with six or more sub-sections
PATTERN One visual step down from the primary bar — smaller type, thinner underline, identical interaction. Stack both into one sticky block so they can never overlap.
1.3

Split a long page into sub-tabs, not a long scroll

When a screen accumulates more than about six independent cards, promote them to named sub-tabs.

A nine-card settings page has no landmarks; users scroll hunting a heading they half remember. Names in a row are scannable, linkable and countable.

USE IN settings, admin configuration, reports, account areas
PATTERN One panel per concern, defaulting to the most-used. Label each with the thing, not the verb.
1.4

Summary numbers link to their explanation

Every figure, badge and count is clickable and lands on the screen that itemises it.

A number with no route to its detail invites a support question. The link is one line of code and removes the question entirely.

USE IN dashboards, KPI cards, notification counts, status chips, list headers
PATTERN KPI card as a button. Navigating also pre-applies the filter that produced the number, so the detail view reconciles.
1.5

One close affordance per dialog

A dialog has an X at the top right and nothing else meaning the same thing.

Two closes make users pause to work out whether they differ. They never do.

USE IN every modal, drawer, sheet and popover
PATTERN X top right for dismissal; the footer carries only Save and Cancel. Multi-step dialogs keep Back in the body, never a second Close.
1.6

No dead ends

Every terminal screen — closed, expired, denied, unavailable — offers a route onward.

A dead end turns a small obstacle into an abandoned session. Users will not hunt for an alternative you did not name.

USE IN out-of-hours states, expired links, permission failures, completed flows
PATTERN State the situation, give the fact needed next (when it reopens, who to contact), then one or two actions that still work.
SECTION TWO

Configuration instead of hard-coding

Every string, rate and rule baked into a screen becomes a support ticket the day the business changes. The test is one question: would a customer have to ask you to change this?

2.1

No hard-coded user-facing copy

Every string an end user reads — headings, buttons, empty states, tag lines, footers — is editable by an administrator.

Copy changes constantly and never warrants a release. Hard-coded text is the most common reason customers return asking for a trivial fix.

USE IN any customer-facing surface, white-labelled products, multi-tenant systems
PATTERN A "words your users see" panel: grouped, labelled by where each string appears, with the default as placeholder text so a cleared field falls back rather than blanking the screen.
2.2

Brand identity is configuration, used everywhere

Logo, legal name, address, contact details and signatory live in one block, and every screen and document reads from it.

The same details otherwise get retyped into each letterhead, invoice and header, then drift apart. One source means one edit.

USE IN anything that prints, emails or exports; anything white-labelled
PATTERN Identity settings with an image upload and preview. Documents bind to it rather than embedding copies.
2.3

Rates, rules and thresholds are settings

Tax rates, fees, notice periods, time limits and retention windows are configurable, never constants.

These change by regulation or policy, not by release cycle, and the change is usually urgent.

USE IN anything financial, contractual, legal or time-bound
PATTERN Common values as quick-pick chips plus a free field, and a worked example under the field showing the effect of the current value.
2.4

Optional features are switchable per surface

Anything a user can request or trigger can be switched off by the administrator, individually.

Capacity, staffing and appetite vary. A feature the operator cannot honour is worse than a missing one, because it makes a promise.

USE IN request buttons, optional data collection, notifications, prompts, self-service actions
PATTERN Grouped switch list with a live summary naming exactly what the end user will now see — including the case where everything is off.
2.5

Presets over bulk toggling

Long switch or permission lists carry named presets that set many values at once, still overridable individually.

Twenty switches is a decision nobody wants to make twenty times, and getting one wrong is silent.

USE IN permissions, feature flags, notification preferences, report columns
PATTERN Preset buttons above the list, a granted count per group, and Clear all. Applying a preset never hides the underlying values.
2.6

Separate today's setup from permanent settings

What changes every day gets its own screen; what changes rarely stays in settings.

Mixed together, the daily task is buried among configuration nobody touches, and permanent settings get changed by accident.

USE IN rostering, availability, capacity, daily notices, shift handover
PATTERN A "today" screen with the day's decisions and a same-as-last-time shortcut; settings holds the defaults it starts from.
2.7

Mark mandatory and optional explicitly

Required fields are marked, and the screen says how many remain.

Users otherwise discover requirements by failing to submit, which is the most expensive moment to learn them.

USE IN every form, especially long configuration and anything feeding a document
PATTERN An asterisk after the label text, never on its own line, plus a live readiness line naming what is outstanding.
SECTION THREE

Input and data entry

The cheapest bug fix is an input that cannot accept the wrong value in the first place.

3.1

Searchable dropdowns above about eight options

Any list that can grow past a handful gets a type-to-filter field.

Scanning beats scrolling until roughly eight items; past that, typing wins and keeps winning as the list grows.

USE IN categories, assignees, locations, tags, accounts, products
PATTERN One field with a chevron: focus opens the full list, typing filters it, the chevron opens and closes it, selecting closes it and shows the value.
3.2

Create from inside the dropdown

When the typed value does not exist, an add row appears at the top of the list and creates it in place.

Sending a user to settings mid-task loses the task. Most abandoned records are abandoned at exactly this point.

USE IN any taxonomy the user legitimately extends: categories, tags, roles, units, methods
PATTERN Add row only when there is no exact match. Creation selects the new value, writes an audit entry, and where the value has consequences collects them inline.
3.3

Constrain the format rather than validating it

Dates, times, months and numbers use native pickers and numeric inputs, so an invalid value cannot be typed.

A free-text date field guarantees ambiguity and a validation message. A picker removes the whole class of error.

USE IN everywhere a date, time, duration or quantity is captured
PATTERN Store the machine format, display the human one, and keep paired ranges self-correcting so the end can never precede the start.
3.4

Show the derived value as it is typed

When two representations of one quantity exist, entering either shows the other immediately.

Users think in whichever unit suits the moment. Making them convert invites arithmetic errors in the one place errors matter.

USE IN discounts, tax, margins, currency, progress, allocation
PATTERN Two bound fields plus a live consequence line in plain words. Amounts on legal or financial documents also print in words.
3.5

Bulk selection on long lists

Multi-select lists offer select-all, clear-all and group-level selection.

The common intent is "nearly all" or "none". Expressing that one item at a time is slow and error-prone.

USE IN permissions, rosters, notification lists, report columns, batch actions
PATTERN Select-all beside a live count, per-group toggles, and a repeat-last-time shortcut where a previous selection exists.
3.6

Design for more than twenty of anything

Every list of records assumes it will be long: search, filter, grouping and a show-more path from the start.

Lists built for demo data break on the first real customer, and retrofitting search means rebuilding the screen.

USE IN people, items, transactions, locations, documents, log entries
PATTERN Search, sensible grouping, a capped default view with an explicit expander, and a count so the user knows what is hidden.
3.7

Full CRUD, or a stated reason why not

Anything a user can create, they can read, edit and remove — or the screen says why not.

Create-only records make the first typo permanent, and permanent typos flow into every report built on them.

USE IN any user-entered record: entries, notes, line items, contacts, configuration rows
PATTERN Edit and remove on every row, with reason capture and an audit entry where the record affects money, compliance or someone else's work.
SECTION FOUR

Lists, tables and reporting

A table users cannot sort, search or export is a table they will re-key into a spreadsheet.

4.1

Sortable columns with visible direction

Column headers sort, and the active column and direction are shown.

Sorting is how people answer "biggest", "oldest", "whose". Hidden sort state makes users doubt what they are reading.

USE IN every data table
PATTERN Header as a button with an arrow on the active column; clicking it again reverses. The most useful order is the default.
4.2

One search box across all columns

A single field matches every meaningful field in the row, and works alongside the filters.

Users search for the fragment they remember, not the field it lives in. Per-column search asks them to know your schema.

USE IN logs, transactions, directories, catalogues, history
PATTERN Search plus a live result count and a Clear action, and a no-matches state that names the term and offers to clear it.
4.3

Every report exports

Any screen presenting figures exports what is on screen — current filters and range included.

Reports get emailed, filed and reconciled elsewhere. Without an export users screenshot or retype, and the numbers stop matching.

USE IN reports, ledgers, logs, audit trails, list views
PATTERN Export in the panel header, a confirmation naming row count and columns, and the export itself recorded in the audit trail.
4.4

One date range, obeyed by everything

A single range control governs every figure on the screen, and every label reflects the chosen range.

A panel that silently ignores the filter is worse than no filter: the number looks authoritative and is wrong.

USE IN reports, dashboards, analytics, statements
PATTERN Quick presets plus custom from and to pickers, a derived duration summary, and copy that adapts — never "today" while showing a month.
4.5

A ledger view beside the summaries

Aggregated reports are paired with a one-row-per-record listing for the same range.

Summaries answer "how much"; only the ledger answers "which one". Reconciliation and disputes always need the second.

USE IN financial reporting, activity reporting, operational history
PATTERN A ledger sub-report with every identifying column, rows that open the underlying record, and its own export.
SECTION FIVE

States and feedback

The states nobody designs are the ones every user eventually sees.

5.1

The eight states, every time

Each data surface has a designed empty, first-run, loading, partial, error, success, permission-denied and offline state.

These are not edge cases. Empty is what every new customer sees first, and error is what they remember.

USE IN every list, table, form, dashboard and detail screen
PATTERN A state set per surface. Empty explains what will appear and offers the action that fills it; error names what failed and what to try; loading holds layout to prevent reflow.
5.2

Distinguish "nothing yet" from "nothing found"

An empty list because nothing exists reads differently from one because filters excluded everything.

One needs an onboarding action, the other needs the filter cleared. The same message serves neither.

USE IN anywhere search or filters sit above a list
PATTERN First-run empty state with the create action; no-matches state naming the active filters with a one-tap clear.
5.3

Confirm before anything destructive or financial

Deletions, cancellations, closures, discounts and irreversible sends confirm first, naming the consequence.

One-click destruction on a shared operational screen is a data-loss incident waiting for a busy afternoon.

USE IN delete, cancel, close, refund, void, send, publish
PATTERN One shared confirm dialog stating what will happen in specifics — not "are you sure" — with the destructive action labelled by its verb.
5.4

Undo on anything reversible

Reversible actions confirm afterwards with a message carrying Undo, rather than asking first.

Undo is faster than a confirmation for the ninety-nine cases that were intentional, and kinder for the one that was not.

USE IN archiving, status changes, list edits, clearing, marking done
PATTERN A message describing the action with Undo beside it, live for several seconds. Reserve confirmations for what undo cannot reach.
5.5

Say what happened, in specifics

Confirmations name the record, the values and the consequence, and adapt to what actually occurred.

"Saved" gives the user nothing to verify against. A specific message doubles as a receipt.

USE IN every write action
PATTERN Compose the message from the real values; if the count is one, do not claim a batch.
5.6

Only offer actions that will work

Where an action depends on a capability the record may lack, show the capability and withhold the action.

A button that silently does nothing is worse than an absent one: the operator believes the task is done.

USE IN notifications, messaging, printing, integrations, exports, device-dependent actions
PATTERN A capability badge per row, the action rendered only when viable, and the fallback named where it is not.
5.7

Degrade honestly when a dependency fails

If a device, provider or integration is unavailable, the record still saves, the failure is visible, and a retry exists.

Coupling data capture to an unreliable side effect loses real work. The failure belongs on screen, not in a log.

USE IN printing, payments, messaging, sync, third-party APIs
PATTERN Persist first, then attempt. Show a failed badge on the record with an explicit retry, and mark retries as retries.
SECTION SIX

Trust, attribution and recovery

Shared operational software needs to answer "who did this" without an engineer.

6.1

An audit trail with date, time, actor and target

Every consequential action records what changed, when — date and time both — who did it, and which record it touched.

Disputes are resolved by the log or by argument. A log without a date only proves something happened eventually.

USE IN anything multi-user: money, permissions, configuration, deletions, overrides
PATTERN A dedicated log screen with type filters, cross-column search, sortable columns and export — and confidential entries marked.
6.2

Attribution on screen, not only in the log

Records show who created, changed or approved them, in the interface.

Visible attribution answers the question where it is asked, and quietly improves behaviour.

USE IN approvals, discounts, cancellations, notes, status changes
PATTERN A "by" line on the row or detail header, naming the person rather than an account identifier.
6.3

A consistent identity spine

The identifiers that locate a record appear on every screen that touches it, in the same order and place.

Staff cross-reference between screens constantly. A stable spine means never hunting for the same reference twice.

USE IN order and case management, tickets, logistics, healthcare, field service
PATTERN An identifier strip component fed the same fields everywhere, including on printed artefacts.
6.4

Record the origin of every entry

Where a record can arrive by several routes, store and show which one, and when.

Origin is what makes reporting on channels, self-service adoption and error sources possible at all. It cannot be reconstructed later.

USE IN multi-channel intake: self-service, staff-entered, imported, API
PATTERN A source field on the record, shown on the detail view and available as a report column and filter.
6.5

Resumable sessions on fixed entry points

When a session is anchored to a durable thing rather than a browser, returning to the entry point restores the live state.

Users close tabs, lose signal and switch devices mid-task. Losing their progress is a self-inflicted failure.

USE IN kiosk and QR entry points, shared links, multi-device workflows, long forms
PATTERN Resolve state server-side from the durable key, not client storage. Persist drafts too, and define explicitly when the session ends.
SECTION SEVEN

Language and numbers

Vocabulary is interface. A word a new employee has to translate is a word that will be remembered wrongly.

7.1

Plain-language status, never internal codes

Statuses read as words someone understands on their first shift.

Internal vocabulary forces every user through a translation step, and translations get remembered wrongly.

USE IN every status, state machine, error and log entry
PATTERN One status vocabulary defined once and used identically across surfaces, exports and printed artefacts.
7.2

Money is itemised, never a single opaque total

Wherever a total appears, its components appear as separate lines.

An unexplained total is the most disputed element in any interface, and the dispute costs more than the line items.

USE IN checkout, invoicing, payroll, quoting, expenses
PATTERN A totals block — components, adjustments, tax, then the payable emphasised — in the same order everywhere including print.
7.3

Pass-through money is not income

Amounts collected on someone else's behalf sit in their own ledger and stay out of revenue, while still appearing in what the payer owes.

Folding them into income overstates revenue and understates a liability. It is an accounting error, not a display choice.

USE IN tips, deposits, taxes collected, agent collections, reimbursements
PATTERN A separate ledger with its own settlement state; summary screens show the figure while stating it is excluded.
7.4

Derive every figure from one source

Counts and totals appearing in several places are computed once and read everywhere.

Independently computed figures drift, and once two screens disagree users stop trusting both.

USE IN dashboards, badges, report headers, exports
PATTERN One derived value per concept. Labels build from it too, so a count of one never reads as a plural.
7.5

Time from the device, with the source declared

Time-of-day copy, day names and relative times derive from the user's clock, and the interface says which clock it means.

Software that says "good evening" at breakfast reads as broken, and ambiguous timestamps are unusable across zones.

USE IN greetings, schedules, opening hours, deadlines, logs
PATTERN Display from the local clock; keep operational records on the business clock and label anything readable either way.
SECTION EIGHT

Scale, multiplicity and concurrency

Most expensive rewrites start as a one-to-one assumption nobody questioned.

8.1

Question every one-to-one assumption

Before building, ask whether the real world allows many where the model assumes one — and make the singular case a group of one.

Retrofitting one-to-many touches every screen. Modelling it as a collection from the start costs almost nothing.

USE IN accounts to users, orders to recipients, records to owners, assets to locations
PATTERN Store the collection; render the single-member case exactly as before so nothing regresses, and show the group identity when there is more than one.
8.2

Design the many-at-once case

Anything that can arrive one at a time will arrive ten at once. Decide now how ten look.

Interfaces designed for one alert become unusable under load, which is exactly when they matter.

USE IN alerts, requests, approvals, incoming messages, queues
PATTERN Group by type with a count, a batch clear per group, a capped view with an expander, and ordering by urgency rather than arrival.
8.3

Handle two people acting on one record

Concurrent actions are anticipated: the second actor is told what the first already did.

Shared tools mean double-processing, and the resulting duplicates are painful to unpick.

USE IN queues, approvals, dispatch, shared inboxes, payments
PATTERN Show in-progress state with the actor's name; block or warn on the second attempt rather than silently applying it twice.
8.4

Ordering rules that are fair and visible

Where position matters, it derives from a server-stamped fact, is shown to everyone, and any override is logged.

Invisible ordering invites accusations of queue-jumping, and staff cannot defend a rule they cannot see.

USE IN queues, waitlists, ticketing, dispatch, prioritised work
PATTERN Position from a server timestamp, displayed to both sides, with reordering treated as an audited exception.
8.5

Layer notification, most reliable first

Reaching a user uses several mechanisms in order of reliability, and the interface never implies more than the available layer delivers.

Push and in-page channels fail routinely. A single-channel design fails silently, which is the worst kind.

USE IN anything where a user waits to be called, alerted or summoned
PATTERN A durable human-readable identifier as the base layer, live updates while the surface is open, optional contact details for the closed case, and per-record capability shown to staff.
SECTION NINE

Roles, access and credentials

9.1

Role presets with per-action overrides

Access is granted by applying a role preset, then adjusting individual permissions.

Roles cover the common case; reality always has exceptions. Supporting only one of the two guarantees workarounds.

USE IN any multi-user product
PATTERN Grouped permission list with presets, granted counts per group, sensitive permissions marked, and grants recorded in the audit trail.
9.2

Credential issuance belongs to the create flow

Creating a user runs through to access: record, credential, permissions, and a way to hand the credential over.

Splitting these means users exist who cannot sign in, and nobody knows whose job the next step was.

USE IN staff, member and partner onboarding
PATTERN A stepped dialog — details, credential shown once with copy and send actions, then access — reachable again later from the row.
9.3

Permission-denied is a designed screen

A user without rights sees an explanation and who can grant them, not a blank panel or a silent redirect.

Unexplained absence reads as a broken product and generates a support contact every time.

USE IN every gated screen and action
PATTERN A denied state naming the permission and the person to ask. Gated actions are visible but disabled with a reason, or hidden consistently — never a mixture.
SECTION TEN

Layout, responsiveness and artefacts

10.1

Fluid by default

Rows of fields and cards wrap and shrink; only genuinely fixed formats keep fixed dimensions.

Fixed-width rows are the commonest source of overflow, and they break at the widths real users have.

USE IN every form row, card grid, toolbar and table container
PATTERN Flex or grid with gap, wrapping enabled, minimum widths that permit shrinking, no fixed heights on anything holding text, and horizontal scroll confined to wide tables.
10.2

Layout follows density, not device

Screens are designed by information density and posture — glanceable, operational, analytical — rather than by nominal breakpoint.

The same user opens the same product on a phone in a corridor and a desktop in an office, with different intent each time.

USE IN any product used across contexts
PATTERN Consumer and field surfaces stay light with large touch targets; administrative surfaces go dense. Both reflow rather than switching to a separate design.
10.3

Printed and exported artefacts are first-class

Documents the business hands over are designed, not derived from a screen print.

These artefacts represent the organisation externally and often carry legal weight. A screenshot of a web page does not.

USE IN invoices, receipts, letters, certificates, tickets, statements, labels
PATTERN A print-owning document shell, identity pulled from settings, variables merged from the record, and unfilled placeholders visibly marked so nothing is signed blank.
10.4

Consolidate before adding

Before building a screen or component, check whether an existing pattern covers it, and extend that instead.

Near-duplicate screens diverge, then need fixing twice, and teach users two ways to do one thing.

USE IN every addition to an existing product
PATTERN One dialog, one table, one combobox, one message, one confirm — parameterised. If a second is genuinely needed, name the difference out loud.
10.5

Put information where it is asked for

If a fact is useful on a screen, it appears there — even if it already exists somewhere else.

Making users navigate to assemble one answer is the most common and least visible usability failure.

USE IN detail views, list rows, confirmations, printed artefacts
PATTERN For each screen, name the question the user arrived with, and check the answer is on it without a click.
10.6

Themed interaction states, never browser defaults

Hover, pressed, focus, selected and disabled are defined once in the system and inherited everywhere.

Undefined states are where a considered product suddenly looks unfinished, and default focus rings fail keyboard users quietly.

USE IN every interactive element, including links added later by content editors
PATTERN Hover and pressed from the accent ramp, a visible focus ring on keyboard focus, disabled at reduced opacity, and default link colours defined before any link exists.
BEFORE YOU BUILD

Four questions that catch most of it

1. Would a customer have to ask us to change this?
2. What does this screen look like with nothing on it, and with ten thousand things on it?
3. What happens if two people do this at the same time?
4. If this action fails, does the user find out?
