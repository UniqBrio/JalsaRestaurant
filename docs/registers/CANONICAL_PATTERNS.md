# Canonical Patterns

> **One blessed idiom per cross-cutting concern.** Inventing a second way is a defect, not a
> preference.
>
> Read the reference file and mirror it. If a concern has no row yet, **bless one first**, then
> follow it.
>
> Append-only. A row is amended in place, dated, with the superseded language kept
> (`AMENDED 2026-03-14 from "…"`). IDs are never reused.

| ID | Concern | The blessed pattern | Reference |
|---|---|---|---|
| CP-1 | Identity resolution | Tri-state: `resolving` / `none` / `value`. Never conflate "still loading" with "genuinely absent" — that is what renders an empty state over data that is about to arrive. | `src/lib/session.ts` |
| CP-2 | Deriving from auth | Gate every derived value until authentication has hydrated. A permission computed from a null identity is `false`, and `false` renders as a denial. | `src/hooks/useAuthReady.ts` |
| CP-3 | Async loaders | Every loader terminates in a `finally`. A spinner that can hang forever is a failure, not a slow success. **AMENDED 10-Sep-2026** — the loader terminating is only half of it; the WAIT must terminate for the user too. A full-surface wait **says what is being made** (configurable copy, never a hard-coded "Loading…"), and past a threshold **stops pretending**: it reports that the wait is abnormal and offers a route onward, because a waiting screen is the one surface with nothing else to click. Thresholds are configuration, and a misconfigured pair is repaired rather than left with the stalled state unreachable. `rung: starter/tests/unit/loading.unit.spec.ts` | `src/hooks/useAsync.ts` · `src/lib/loading.ts` · `src/components/LoadingScreen.tsx` |
| CP-4 | Data access | One client module. Every read and write goes through it. No component constructs its own. | `src/lib/api-client.ts` |
| CP-5 | Error classification | `classifyError()`. One decision per catch site. | `src/lib/errors.taxonomy.ts` |
| CP-6 | Permission denial | Honest no-access state. **Never** re-authenticate, never render an empty list that looks like real data. | `src/components/NoAccess.tsx` |
| CP-7 | Sub-page mounting | Sub-pages of a section mount the same way as their siblings. Read one before writing another. | `src/components/TabRow.tsx` (and the section layout that hosts it) |
| CP-8 | Fixed-chrome clearance | Content clears fixed chrome using the named layout constant. Never a hand-picked padding value. | `starter/design/tokens.json` → `layout.bottomChromeClearance` |
| CP-9 | Safe writes | Find-then-update-else-insert, or an explicit conflict clause, against the table's real unique constraint. | `src/lib/upsert.ts` |
| CP-10 | Multi-write flows | One server-side transaction. A cascade that can half-apply will. | `supabase/functions/_shared/tx.ts` |
| CP-11 | Customer-facing failure text | From the wording table. Never a raw engine string, ever. | `src/lib/errors.taxonomy.ts` |
| CP-12 | Calling an external model provider | Server-side only · minimal payload · output treated as untrusted · graceful degradation · pinned versions. | `supabase/functions/_shared/provider.ts` |
| CP-13 | Animation | Configuration is centralised in motion tokens. Motion **never** gates interactivity, and reduced motion collapses to the end state. | `design/tokens.json` → `motion` |
| CP-14 | Input dialogs | Backdrop tap does **not** dismiss. Typed data survives. Closing with unsaved changes confirms first. | `src/components/Dialog.tsx` |
| CP-15 | Dates | Entry through the shared picker · display in one canonical format · storage always ISO. **AMENDED 06-Sep-2026** (was: the preceding sentence only): a date arriving from **import, paste or an API** bypasses the picker, so it must be **unambiguous or rejected** — `01/09/2026` is two different days and accepting it silently picks one. Require ISO, or reject naming the ambiguity and the accepted format. | `src/lib/dates.ts` |
| CP-16 | Focus | First field focused on dialog open; searchable dropdowns focus their search input. Focus is computable — automated, never eyeballed. | `src/components/Dialog.tsx` |
| CP-17 | Overflowing tab/filter rows | The row **scrolls**. Never capped, never a "More" affordance that hides items behind a lid. | `src/components/TabRow.tsx` |
| CP-18 | Bulk selection | Opt-in mode · scope is the **visible** set · the write shape follows the failure shape (partial failure must be reportable per item). **AMENDED 10-Sep-2026** — the selection now has a stated shape, because "scope is the visible set" was a sentence nothing implemented. **A checkbox on every row and a THREE-STATE checkbox in the header**: none · some · all, `some` rendering indeterminate, because a checkbox showing plain "off" over four selected rows tells the user something false about what their next click will do. Clicking the header while partial **selects the rest** — clearing throws away work done click by click, and a selection has no undo. **A filter change drops what left the view and SAYS how many**: a selection that outlives its filter reaches records the user cannot see, which is the greedy select-all defect arrived at slowly. Shift-select runs over the **visible** order, never the underlying data order. Bulk actions obey CP-28: the destructive one confirms with the count and the scope named, the reversible one goes straight through with Undo. `rung: starter/tests/unit/selection.unit.spec.ts` | `src/lib/selection.ts` · `src/components/SelectionColumn.tsx` · `src/components/BulkBar.tsx` |
| CP-19 | Visual emphasis | A filled or coloured control is a semantic claim. Peers share one treatment; at most one is primary. | `src/components/BulkBar.tsx` · prose: [docs/04](../04-ARCHITECTURE-AND-DESIGN.md#5-interface-design) |
| CP-20 | Theme-aware assets | CSS-driven variant switching, never JavaScript. One variant carries the alt text. | `src/theme/ThemedImage.tsx` |
| CP-31 | A path crossing from the shell into an interpreter | **Argv is translated; SOURCE is not.** `node "$ROOT/x.mjs"` resolves on every platform because the shell rewrites path-shaped arguments on the way out. The same string interpolated into JavaScript *source* — an import specifier, a `readFileSync` argument — is **data**, nothing rewrites it, and Git Bash's `/c/...` reaches Node as `C:\c\...`. So: **source `scripts/lib/shpath.sh` and convert at the boundary** — `$(jspath …)` for anything `fs` will open, `$(jsurl …)` for an ESM specifier, which is the only form Node accepts (a bare `C:/…` is `ERR_UNSUPPORTED_ESM_URL_SCHEME`, the drive letter parsing as a scheme). Convert **once** into a `_js` / `_url` variable when a harness uses it repeatedly. **Never `2>/dev/null` the interpreter** — RC-012 cost twelve false accusations because `ERR_MODULE_NOT_FOUND` was discarded, and a harness that cannot say "I could not run" reports "your code is broken" instead. `rung: scripts/shpath.test.sh` (case 4 sweeps the tree, case 5 proves the sweep fires) | `scripts/lib/shpath.sh` · `scripts/ratchet.test.sh` (the one-line form) · `scripts/theme-build.test.sh` (the converted-once form) |
| CP-30 | Installability | **Every application is a PWA, and none of it is configuration.** A generated web app manifest, a service worker, an offline fallback and launcher icons ship in the box; `src/app/layout.tsx` links the manifest and mounts `<PwaProvider/>`, which registers the worker. Four rules keep it honest. **(1) The manifest is GENERATED from `design/tokens.json`** — `theme_color` and `background_color` are colour decisions, and colour lives in exactly one file; a rebrand reaches the installed window or the app and its chrome drift apart. **(2) HTML is never cache-first** — a cache-first navigation pins users to a version that no longer exists, and the worker deciding whether to fetch the fix is the broken one. Network-first, cache as fallback, offline page as last resort. **(3) The data layer is never cached** — no API responses, nothing non-GET, nothing cross-origin, nothing carrying credentials. A cache that serves one user's data to the next is a security defect, and it arrives as a well-meaning "cache the API too". **(4) An update is offered, never imposed** — the worker does not call `skipWaiting()`; the user is told a version is ready and chooses, because reloading code under a running session loses the form they were filling in. `rung: starter/tests/unit/pwa.unit.spec.ts` · `scripts/audits/check-pwa-baseline.mjs` (gate G12) | `src/lib/pwa.ts` · `src/components/PwaProvider.tsx` · `src/app/layout.tsx` · `public/sw.js` · `design/tokens.json` → `app` |
| CP-29 | Money on screen | **Never a single opaque total.** Wherever an amount is payable, its components are separate rows — items, adjustments, tax, then the payable emphasised — in ONE order, on every surface that shows that money: screen, dialog, export and print alike. Four rules make the figures trustworthy. **(1) The rows shown add up to the total shown** — round each row once, then sum the ROUNDED rows; summing raw values and rounding at the end produces a breakdown that is off by a paisa, which reads to a customer as an arithmetic bug because it is one. **(2) Pass-through money is not income** — amounts collected on someone else's behalf (tax, deposits, tips, agent collections) appear in what the payer owes and are excluded from revenue; folding them in overstates revenue and understates a liability. **(3) An impossible total is reported, never clamped** — a discount larger than the charge produces a negative payable and a warning, because flooring it at zero hides a data-entry mistake and quietly gives the money away. **(4) One calculation, one renderer** — every module that quotes, bills or charges feeds the same breakdown to the same component, and neither re-implements currency formatting. Two screens disagreeing about a total is how a customer stops believing every number the product shows, including the right ones. `rung: starter/tests/unit/pricing.unit.spec.ts` | `src/lib/pricing.ts` · `src/components/PricingPanel.tsx` |
| CP-28 | The reversibility decision | **Irreversible → confirm FIRST. Reversible → act, say what happened, and carry Undo in the message.** One decision, made per action, and getting it backwards is worse than getting it wrong: a confirmation on something reversible trains the user to click through confirmations without reading them, which is exactly how the irreversible one gets clicked through too. The confirm is `ConfirmDialog` (CP-14), naming what will happen in specifics and labelling the button with its verb, never "OK". **Undo is a DEFERRED COMMIT, not a compensating write**: the effect is held for the undo window and committed when it closes, so Undo is a local cancel that cannot fail — the compensating-write version tells the user "Undone" about a change that is still there when the reversing write fails. Where a write genuinely cannot be deferred, do not offer undo; confirm instead, and say so. The queue **never drops a pending action** — overflow commits early and reports it, and unmount drains it, because a silently discarded commit is an action the user believes happened. Messages are composed from the real values, so a count of one never reads as a plural or claims to be a batch. `rung: starter/tests/unit/undo.unit.spec.ts` | `src/lib/undo.ts` · `src/components/ToastHost.tsx` · `src/components/ConfirmDialog.tsx` |
| CP-27 | The audit trail | Wherever **RBAC is enabled**, every account creation, role assignment and feature-access change is recorded: **what changed · screen/module · previous value · new value · modified by · modified at · remarks**. Four rules make the rows trustworthy, and each has a spec. **(1) An entry with no real actor is not an entry** — a background job is `System (<process>)` and says which; a *user* action whose identity did not resolve is `Unknown (<id>)`, never dressed up as System (RC-007 shipped exactly that), and the view **counts** the unattributed so the resolution defect gets fixed. **(2) A row never carries the secret it audits** — *Password changed* is the record, the password is not; a faithful before/after log is a credential store with a search box. **(3) A change that did not happen must not appear** — arrays compare as **sets**, so reordering roles is not a role change, and `null`/`undefined`/`""` are one absence. **(4) Append-only** — the module exports no updater and no deleter, and the table has no edit or delete affordance. The view **composes CP-23** for search / module filter / date presets / sort and **CP-21** for its seven columns, rather than building either again. `rung: starter/tests/unit/audit.unit.spec.ts` | `starter/src/lib/audit.ts` · `starter/src/components/AuditLogTable.tsx` |
| CP-26 | Deleting a record | **Every entity declares ONE delete model, at design time, in writing: ARCHIVE or REMOVE.** The defect is never "the backend soft-deletes" — it is the two layers disagreeing about what delete means, each self-consistent, so a row returning on refresh, a re-add hitting a unique constraint and a stale id 404-ing all look like three unrelated bugs. **ARCHIVE:** reads filter it out by default · the unique index is **partial** (`where status = 'active'`) so the name is reusable · the control says *Archive*, never *Delete* · a restore path exists. **REMOVE:** the row is gone, dependants are handled by a deliberately chosen `on delete` rule, and the confirmation says it cannot be undone. **A delete policy added by reflex is how the audit trail disappears.** The assertion is a **round trip** — act, then re-read through the same path the list uses — never the response to the delete call, which only proves the request was accepted. `rung: starter/tests/functional/reference.functional.spec.ts` (three delete journeys) | `starter/supabase/migrations/00000000000000_reference_migration.sql` (status + partial index + no delete policy) |
| CP-25 | Editing an existing record | An edit surface **loads the record before it renders**: fields arrive populated, multi-selects arrive selected, and the form is in edit mode addressed by the record's **database id** — never the create form with a different title, and never keyed by a display label two records can share. **Saving an unchanged edit is a no-op**: every field the form did not load still round-trips unchanged, because a field sent back empty destroys the stored value silently. `rung: starter/tests/functional/reference.functional.spec.ts` | `starter/tests/functional/reference.functional.spec.ts` (edit-parity journeys) |
| CP-24 | Dashboards and analytics | A dashboard is **configuration, not code**: business-agnostic components driven by a `DashboardConfig` (metrics · filters · sections · breakdown ladders). Four honesty rules hold in the implementation: direction is not sentiment (`higherIsBetter`) · growth from zero is `null`, never infinite · an absent value renders as `—`, never `0` · role-restricted metrics are REMOVED from the resolved config, never CSS-hidden. Visualization is chosen by the question it answers; filters reuse CP-23; no charting dependency. `rung: starter/tests/unit/analytics.unit.spec.ts` | `src/components/analytics/` · `src/lib/analytics/` · `src/lib/analytics/examples.ts` |
| CP-23 | List and table views | Every list carries the standard controls through the shared implementation: **one search box across the module's key fields** (name, phone digits normalised, email, …) · **multi-select contextual filters** · **date presets** — Today · This week · Last week · This month (+ Last month, All time) · **Custom range** — where the data is dated · **ascending / descending sort** on the relevant columns, blanks last · the count shown as *matching / total*. Never a per-module reinvention. `rung: starter/tests/unit/list-controls.unit.spec.ts` | `src/components/ListControls.tsx` · `src/hooks/useListControls.ts` · `src/lib/list-controls.ts` |
| CP-22 | Keyboard operability | Every interactive control is a real focusable element — a native `button`, link or input, never a `div` with a click handler — so Tab reaches it, Enter activates it, and Space selects tab-style controls **for free**. Core workflows are completable keyboard-only, verified by one full keyboard pass. `rung: starter/tests/functional/keyboard.functional.spec.ts` | `src/components/TabRow.tsx` · `src/components/Dialog.tsx` |
| CP-21 | Wide tables | More than **three** columns means the user chooses which columns show and in what order, and the choice **persists**. Reorder with buttons, never drag-only. A column the table is unreadable without is `required` — reorderable, never hideable. `rung: scripts/audits/check-column-control.mjs` (floor: literal `<th>` tables only; dynamic tables are a review item) | `src/components/ColumnControl.tsx` · `src/hooks/useColumnPrefs.ts` |

## Adding a row

1. Confirm no existing row covers the concern. Two rows for one concern is the failure this
   register exists to prevent.
2. Write the pattern as a **rule**, not a description: something a reviewer can hold a diff up
   against.
3. Name a **working reference file**. A row with no reference is an opinion.
4. If the row came from an incident, add a sentence saying which — the *why* is what makes
   people follow it six months later.
5. Where a rung exists that enforces the row mechanically, name it: `rung: <path>`.
